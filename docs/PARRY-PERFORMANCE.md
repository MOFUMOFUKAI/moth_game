# パリィ時の負荷改善（2026-10-16）

## 変更内容

- 各フレームの移動処理より前に、衝突判定に使う実際の矩形をまとめて取得する。
- そのフレーム内では、移動後のCSS座標との差分を使って判定する。敵ごとに「位置変更→画面配置の再計算」を繰り返さない。
- ブラウザの座標の端数処理を初回に測定し、判定の境界にいる敵の扱いを合わせる。
- 敵が新しく出現した場合や、フレーム外の入力処理では従来どおり実際の矩形を取得する。対象がいないフレームは不要な測定を省く。
- スコア・経験値・レベル・ハートの表示はフレームの最後にまとめ、文字列が変わった要素だけ更新する。ゲーム状態やレベルアップの適用は即時のまま。

## 維持した仕様

通常パリィ半径55px、ジャスト半径40〜52px、判定を5回予約する間隔、380msのクールダウン、無敵の期限、表示サイズ、移動速度、敵の下寄せ70%の判定、反射直後の判定拡大、反射弾の移動区間を使ったすり抜け防止処理は変更していない。

共通タイマーの追いつき処理、虹色の演出、背景描画、音声再生も今回は変更していない。

## 検証と限界

Chromeのスマホ相当表示（390×844、CPU速度を4分の1に制限）で、乱数を固定し、敵20体を置いて約1.2秒計測した。変更前は変更前のソースを別の検証ページで読み込んだ。

| 条件 | 変更前の配置再計算回数 | 変更後の配置再計算回数 |
| --- | ---: | ---: |
| 敵20体の落下 | 824 | 72 |
| 敵20体の落下中に空振りパリィ | 830 | 69 |

敵の落下が続く条件では配置再計算を約91〜92%削減した。これはゲーム全体の処理時間や実機のフレーム落ちが同じ割合で減るという意味ではない。矩形取得そのものの呼び出し回数は大きく減らしておらず、読み取りと書き込みの交互実行を減らした結果である。

別の連続撃破シナリオでは、20体を同じ位置の列に置き、元の落下を止めて反射・撃破処理を検証した。変更前後で同じ得点（時間加点込み44,180）になった。この条件は通常プレイと異なり、落下時の負荷改善を測る用途には使っていない。

`tools/collision-browser-check.cjs` は320・390・1000pxの画面で、敵3サイズ、整数・小数・負の座標、複数の移動量を組み合わせ、ブラウザが実測した矩形と最適化後の矩形、およびパリィ境界の判定を比較する。既存の操作・演出のブラウザ検証と、追加の自動テストでも判定範囲、初回判定の遅延、無敵、クールダウン、連続更新中の位置、表示の最終値を確認する。

実機のiPhone/Safari・Androidでの処理落ちは未確認。PC上では変更前から明確なフレーム落ちを再現していないため、実機での改善率は未確定。残る引っ掛かりがあれば、虹色フィルター・音声・背景描画を切り分けて調べる。

## 虹色演出を止める比較版（2026-10-18）

`src/game.js` 冒頭の `ENABLE_RAINBOW_VISUAL` を `false` にして、ジャストで反射した敵への `.rainbow` クラス付与だけを停止した。虹色のCSS定義は残している。

元に戻す場合は `ENABLE_RAINBOW_VISUAL` を `true` に変更する。

反射速度、当たり判定、威力、得点、コンボ追跡、無敵時間、ジャストパリィのエフェクトと音声、爆発、移動更新の仕組みは維持する。iPhone 11で同じステージ・同程度の敵数で比べ、ジャスト直後の引っ掛かりが減るか確認するための版であり、フィルターが原因と確定したものではない。
